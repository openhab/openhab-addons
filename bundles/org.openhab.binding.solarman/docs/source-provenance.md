# Source Provenance and Developer Verification

## Upstream Sources

The advanced profile definitions derive from [kellerza/sunsynk revision f1ecbc28e3ccf2b9f87b1ccee85a41628567da43](https://github.com/kellerza/sunsynk/tree/f1ecbc28e3ccf2b9f87b1ccee85a41628567da43).
Its project metadata identifies Johann Kellerman and Apache-2.0 licensing.
NOTICE retains attribution, and src/main/resources/sunsynk/LICENSE is the original complete upstream license, packaged as sunsynk/LICENSE.
The pinned source tree has no root NOTICE file to copy.

| Material                                                          | Source and treatment                                                                                                                    |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Five sunsynk/*.json profile resources                             | Exported from pinned Python definitions and sensor/control classes, including aliases; Apache-2.0-derived metadata                      |
| Differential read/write fixtures under src/test/resources/sunsynk | Expected results obtained by executing the same pinned Python behavior, including boundary cases; attribution follows the pinned source |
| sunsynk/metadata/single_phase.json                                | Three EPL-2.0 binding-origin String metadata additions based on deye_hybrid registers; kept separate from Kellerza JSON                 |
| Generated advanced XML, identifiers and catalog                   | Generated from profile metadata plus those explicit binding additions                                                                   |
| Legacy definitions and Java binding                               | Retain openHAB EPL-2.0 source licensing and existing author attribution                                                                 |
| Independent legacy baseline fixtures                              | Generated by executing recorded official openHAB Java/YAML in isolation; source hashes, revisions and reviewed differences are retained |

The Java interpreter uses the openHAB runtime; Python is development tooling only.
A profile match or generated fixture is software evidence, not hardware qualification.
See the README's hardware table for the reported device scope.

## Building

Use Java 21 and the Maven configuration inherited from the selected openhab-addons checkout.
From this binding module, run:

```shell
mvn spotless:apply clean install
```

Inspect Surefire and Checkstyle/PMD/SpotBugs reports, XML validation, BND output and Karaf verification.
Do not treat an artifact name or absent package-version constraints as evidence of cross-version runtime compatibility.

## Regenerating Profile Data

Use Python 3.12 or newer and a clean checkout of the pinned Sunsynk revision.
The exporter verifies its revision and tracked Python source before loading definition/sensor classes; its adapters replace rendering/MQTT support, not conversions.
It writes both runtime JSON and differential fixtures, so review the complete diff rather than regenerating expectations to conceal regressions.

```shell
python tools/export_sunsynk.py /path/to/pinned-sunsynk src/main/resources/sunsynk
python tools/generate_sunsynk_metadata.py
mvn spotless:apply
```

The pinned set contains 925 Kellerza entries.
The three separate binding additions bring the combined catalog to 928 profile-specific channel types and 351 distinct channel IDs.
Definitions with aliases can share register reads.
The read/write fixture sources remain independent of current Java output.

## Regenerating Examples and Register Reviews

These development tools require PyYAML and consume the bundled definitions; they send no inverter commands.

```shell
python tools/compare_profile_definitions.py
python tools/generate_profile_item_examples.py
python tools/review_single_phase_migration.py --definitions-only
python tools/validate_documentation.py
```

The current single-phase comparison contains 81 deye_hybrid legacy entries and 150 advanced entries, including the three binding additions.
The example generator also refreshes the marked README legacy tables from the independent main fixture, preserving all 94 deye_sg04lp3 and 37 deye_2mppt channel IDs/types/access flags.
The five-family comparison intentionally compares only the 925 pinned Kellerza entries and identifies the matched legacy families explicitly.
Register-tuple or numeric-model agreement is a review candidate, not proof of identical limits, rounding, fault coverage or device behavior.

Historical and main legacy fixtures are described in [the fixture provenance](../src/test/resources/legacy/README.md).
Their exporters compile recorded upstream Java/YAML in isolation and use dependency JARs from a test report; working production classes do not generate expected output.
Keep the historical fixture frozen and review upstream evolution separately.

## Example Validation Scope

The documentation validator checks Item/channel types and units, complete generated lists, README/file consistency, sitemap references, published command options, numeric bounds and local links against checked-in metadata.
It also checks that the selected warning and source attribution are present.
This static review does not install the files, execute commands, validate every model's operating conditions or replace an openHAB UI/runtime test.
